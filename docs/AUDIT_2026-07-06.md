# LiveRig Audit — 2026-07-06

Full review of the repo (`~/Desktop/liverig`), the deployed `/Applications/LiveRig.app` bundle, and the latest Live 12.4 / Extensions SDK capabilities. Deployment state at time of audit: **repo ↔ bundle fully in sync** (HTML, bridge, Remote Script, app all byte-identical). Only `LIVERIG_MEMORY.md` is uncommitted.

---

## Part 1 — Issues & stopgaps (things that will bite later)

Ordered by show-risk, not effort.

### 1. No security on the bridge or HTTP server — HIGH (venue WiFi risk)
- WebSocket listens on `0.0.0.0:8765` with **zero auth**. Anyone on the same WiFi can connect and send transport/clip/volume commands mid-show.
- Worse: `http.server` runs with `cwd=/private/tmp`, so it serves **everything in /private/tmp** to the whole LAN — bridge logs, other apps' temp files, not just the controller page.
- Fix: serve from a dedicated `/private/tmp/liverig_www/` dir; add a simple shared token (`?key=...` checked in `handle_client`, injected into the HTML like `{{BRIDGE_HOST}}`). One evening of work; on home WiFi it's harmless, on a venue's shared network it's an open mixing desk.

### 2. No process supervision after boot — HIGH (mid-show resilience)
`liverig_app.py._boot()` checks the bridge once at +2s, then never again. If the bridge or http.server dies mid-show, the menu bar still says "● LiveRig Running" and the iPad just goes dead. The crash-resync fix (0x4A on reconnect) only helps if something restarts the bridge.
- Fix: a watchdog thread polling `self.bridge.poll()` / `self.http.poll()` every few seconds → auto-restart + menu status flip + notification. This completes the crash-restart story that the full-state-resync fix started.

### 3. Show-critical dependency on Homebrew Python — MEDIUM-HIGH
The bridge venv points at `/opt/homebrew` Python. A `brew upgrade` the week of a gig breaks it; the self-heal rebuild needs **internet + minutes** — exactly what you don't have at soundcheck.
- Near-term fix: a "Pre-Gig Check" menu item that verifies venv health, bridge alive, Remote Script deployed + version match, rig_config served, and a WS round-trip — green/red result in one click.
- Longer-term: vendor `python-rtmidi`/`websockets` wheels into the bundle so first-run and self-heal work offline.

### 4. Hardcoded `~/Desktop/liverig` paths — MEDIUM
`liverig_app.py` (`REPO_RIG_CONFIG`) and `LiveRig.py`'s config search assume your Desktop repo exists. The DMG installer story contradicts this — on any other Mac (or if you ever move the folder), config silently falls back to defaults.
- Fix: canonical config at `~/Library/Application Support/LiveRig/rig_config.json`, with the Desktop repo as a dev-mode override when present.

### 5. Dead M4L plumbing still running in the bridge — LOW (cleanup)
`watch_state_file()` polls `/tmp/liverig_state.json` **20×/second forever**, plus the UDP:9000 listener, HTTP:9090 receiver, and the fake `live_state` default ("Track 1…Track 8", 120 BPM) that gets pushed to every client on connect before real data arrives. All dead since the Remote Script migration (already flagged as pending task #10). Removing it deletes ~150 lines, stops wasted wakeups, and kills the brief stale-default flash on connect.

### 6. No version handshake across the 3 deploy targets — MEDIUM
Stale-deploy has bitten twice already (memory file, 2026-07-01/02). A `LIVERIG_VERSION` string in Remote Script + bridge + HTML, emitted over the existing SysEx feedback and shown in the iPad status bar (red if mismatched), turns the next stale deploy from a debugging session into a glance. Pair with one `scripts/deploy.sh` that syncs repo → bundle → Remote Scripts and md5-verifies all three.

### 7. Bridge broadcast head-of-line blocking — LOW
`broadcast()` awaits each client sequentially under one lock; a hung client stalls feedback to all others. Fine with 1-2 iPads; use `asyncio.gather` with per-client timeouts if a second display/iPad becomes standard.

### 8. mtime-based config sync can clobber hand edits — LOW
`_sync_rig_config()` overwrites the repo config whenever the Setup Tool copy is newer, no content check, no backup. Add: skip if content identical, and write `rig_config.json.bak` before overwriting.

### 9. Known gaps carried from ONBOARDING (still open)
- Setup Tool modal has no fields for: loopers, `markerTrack`, per-keyboard `midiChannel`, adding a 5th+ keyboard — all still hand-edited JSON.
- Missing/corrupt `rig_config.json` on the iPad still silently falls back to the generic default (binding badges exist, but a "config not loaded" banner doesn't).
- Several features still unverified live: section strip, marker prev/next fix, crash resync, Blue Hand. → fold into the Pre-Gig Check above as a one-time test checklist.

## Part 2 — Creative upgrades from Live 12.4 / Extensions SDK (verified against SDK 1.0.0-beta.0 typings in `vendor/`)

The SDK explicitly can't do real-time MIDI/audio — so the Remote Script + SysEx backbone stays exactly right. Extensions shine for **authoring and config**. LiveRig already validated this architecture; these build on it:

### A. One-click setlist/marker sync (SDK: `songCreateCuePoint`, `cuePointSetName`)
The SDK can **create and rename Ableton locators programmatically**. You currently maintain two parallel systems by hand: `Song:` locators and the MARKERS track clips. New Setup Tool command: "Generate locators from MARKERS track" (one locator per section clip, `Song:` prefix on section-1s) — or the reverse, build MARKERS clips from existing locators (`trackCreateMidiClip` + `clipSetName` also exist). Kills the most tedious per-song prep step.

### B. Right-click "Bind to LiveRig" (SDK: `registerContextMenuAction` on MidiTrack/AudioTrack)
Right-click any track → "LiveRig: bind as Stem… / KBD… / Looper…" → tiny picker dialog → writes to the Setup Tool's storage config. Faster and less error-prone than the full modal; naturally fixes gap #9's missing fields as you add each binding type.

### C. Patch snapshots off localStorage → bridge persistence
`patchSnapshots` still live in per-iPad localStorage — a new/reset iPad loses your entire patch library mid-tour. The portable-fader-names pattern (Application Support JSON + push-on-connect + rebroadcast) is already built and proven; apply it 1:1 to snapshots. Pure repetition of existing code.

### D. Section strip → lighting cues (your LD side)
The bridge already knows the current song section in real time (`FB_MARKER_NOW`). Add an outbound OSC sender in the bridge (config-mapped: section name → OSC address/MIDI cue) and LiveRig becomes the timecode-free cue master for your lighting console — sections fire lighting looks automatically as the playhead crosses them. Highest creative-payoff item here given your AV/lighting work, and it's bridge-only (no Remote Script change).

### E. Link Audio (Live 12.4) for the multi-computer rig
The deferred "Option A" multi-computer routing may be partly obsolete: Link Audio streams audio between Link peers with automatic latency compensation — a second laptop's output appears as an input in Live with no hardware. Worth a rehearsal-room test before building any custom routing UI.

### F. Key/scale display on Transport (Remote Script: `song.root_note` / `scale_name`)
Live 12 exposes global root note + scale. One more SysEx feedback code → show "F# minor" next to BPM on the Transport page. Trivial, and useful mid-set with 96 patch slots.

### G. Auto-stem prep for new songs (12.4 stem separation + SDK)
12.4 does stem separation on arrangement time selections and can merge to single tracks. A context-menu extension ("LiveRig: prep stems") could rename the resulting tracks to exactly your `rig_config` stem names (DRUMS, BASS, VOCALS…) so a reference mix becomes a fully rig-bound backing arrangement with zero manual binding.

## Suggested order
1. **#2 watchdog + #1 security** — the two real mid-show risks, both small.
2. **#6 version handshake + Pre-Gig Check (#3/#9)** — ends the stale-deploy class of bug forever.
3. **C snapshots portability** — proven pattern, protects your patch library.
4. **D lighting OSC** or **A marker sync** — first big creative feature, pick by mood.
5. **#5 dead-code cleanup, #4 path portability** — whenever convenient.
